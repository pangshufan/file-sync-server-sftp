# 升级与回滚：0.2 / 0.3 → 0.4 / 0.5

[English](en/MIGRATION.md)

## 升级前

1. 停止旧服务并关闭旧桌面程序。不要让两个版本同时操作一个数据目录。
2. 找到窗口底部显示的应用数据目录；不要把它设置成共享目录。
3. 保留 `ssh_host_ed25519_key`。升级不更换主机密钥，客户端指纹应保持一致。
4. 升级到 0.4，并使用原 Conda 环境启动。首次索引可能需要时间。

## 自动备份和迁移

- 读取旧 `config.json` 时，先在 `backups/<UTC时间>-config-v4/` 保存旧配置及 SQLite 一致性快照，然后为缺少 userid 的账号生成固定标识，写入配置 schema_version 4。
- 数据库首次升级前，还会创建 `backups/<UTC时间>-database-v3/`。通过 SQLite backup API 捕获已提交的 WAL 内容，不是直接复制正在运行的 db 文件。
- 数据库 user_version 升为 3。原文件索引及主机密钥保留；catalog 从现有索引和可用变更记录构建。缺少原变更时间的旧记录使用迁移时 server 时间。
- 旧 `tasks/rounds/deliveries/task_files` 已从运行数据库移除；迁移前备份保留它们，不会合并 v1 成功进度。从 0.3 升级保留原 userid、v2 待同步/成功状态、计数和分页密钥。
- 迁移幂等：正常再次启动不会重复生成 userid 或重复执行版本迁移。备份目录权限为 0700，配置和数据库备份为 0600。
- 新默认值：单连接开启、IP 不限制、同步开启、目录 `/`、起始时间 0、包含 `*`、手动确认。管理员应在投入实际使用前审阅这些设置，尤其是起始时间。

v1 客户端必须升级到 v2；没有旧扩展的兼容别名。普通 SFTP 客户端仍可下载，不受协议版本切换影响。服务端设置为自动时才会自动记录普通下载成功。

客户端旧状态目录首次被新 SDK 使用前，会生成 `client-v1-backup-<时间>.sqlite3`。旧设备身份不再使用；本地摘要缓存可继续复用，v2 新增 server/账号/userid 绑定。新的本地下载目标不代表新的 server 进度：同 userid 在其他目标可能拿不到已确认版本，完整目录请使用普通 SFTP 下载。

0.4 新增登录预算参数及 `authorized_keys`（默认空，保留原密码登录）。旧版本不能直接读取含新字段的配置；回滚必须恢复匹配的配置/数据库备份。0.4 服务启动持有数据目录进程锁，GUI 与无头服务不能同时使用同一个目录。

0.5 增加中英文界面，不变更配置/数据库 schema。userid、目录、权限键、协议字段、版本和同步进度保持原值；界面语言不写入配置，旧错误与日志保留原文。

## 调整起始时间

桌面编辑时先停止服务；运维可编辑配置后热加载，详见 OPERATIONS.md。

- 默认不勾选“从新时间重新开始”：保留旧待同步/失败项及成功版本，按新时间补算新候选。
- 勾选“从新时间重新开始”：保存时出现影响说明和确认框，下一次启动或重载后的队列刷新清除该用户旧状态。它可能跳过较早未完成文件，不能用它替代普通重试。
- 向过去调整时间：重新核对该范围；起始时间是 server 观察时间，不是磁盘文件 mtime。
- 重设会使旧分页令牌失效。客户端从第一页继续查询，不沿用旧页令牌。

配置写入后，重设通过持久的 sync_generation 在数据库中执行一次，避免服务重启重复清空。

## 回滚

1. 停止并关闭 0.4。保留一份当前数据目录，避免丢失升级后的记录。
2. 优先使用 `*-config-v4/` 中同时保存的旧配置和数据库；只有数据库迁移时可使用对应 `*-database-v3/` 快照。查看 `reason.json` 确认来源。
3. 在服务完全停止后恢复那一组 `config.json` 和 `sync.sqlite3`，清理停止状态下遗留的数据库 `-wal/-shm` 文件。不要混合不同备份中的文件。
4. 保持原主机密钥不变，切回备份对应的 0.2/0.3 环境或源代码，再启动。

恢复备份将放弃该备份之后的同步记录。项目不提供自动回滚按钮，避免在连接活动期间覆盖数据库。测试使用临时目录验证了备份、索引版本、旧进度不合并与重复启动，不会替你覆盖正式配置。
